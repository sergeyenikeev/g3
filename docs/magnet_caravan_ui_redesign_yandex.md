# Magnet Caravan: UI/UX Redesign For Yandex Games

## 1. Ключевые проблемы текущего интерфейса

## Статус реализации (апрель 2026)

Уже внедрено в коде:

- главное меню упрощено для growing/advanced стадий: убран постоянный нижний liveops-шум, оставлены 2-3 понятных CTA
- `Задания` раскрываются по запросу отдельной кнопкой вместо постоянной перегрузки первого экрана
- rewarded start booster убран из раннего опыта и остаётся только для advanced-stage, где игрок уже понимает ценность бонуса
- главный CTA `Играть` перепакован: действие осталось коротким, а бонусный старт теперь показывается отдельной подписью, без длинного текста внутри кнопки
- русский copy для daily-потока переписан без `дейлик`, с более понятным `Ежедневный заезд`
- в результатах rewarded CTA теперь показывает конкретную выгоду (`Ещё: +N болтов / ядер`), а не абстрактный множитель
- мастерская переведена в paged-flow: крупные карточки, 4-6 апгрейдов на экран на desktop, 2 карточки на compact/mobile, pager даёт доступ ко всем улучшениям без overlap и микрошрифта
- баннер уровня на компактных экранах перенесён ниже HUD, чтобы убрать наложение с верхней панелью
- сама доска заданий стала компактнее: уменьшена высота пустого контейнера, ключевая награда считывается быстрее, а строки миссий перестали выглядеть как технический лог
- из меню убраны стартовые liveops-toast'ы, которые создавали шум и визуально ломали чистый первый экран advanced-игрока
- leaderboard перестроен в более читаемый goal-view: компактная панель, 3-4 укрупнённые строки вместо плотной таблицы и короткий hint на mobile без лишней перегрузки
- экран результатов на compact/mobile переразложен: убраны наложения и обрезания, карточки получили безопасные отступы, а rewarded-кнопка остаётся читаемой без потери ценности награды
- desktop `Результаты` получили ещё один product-pass: summary теперь начинается со счёта и лиги, имя пилота и лишняя телеметрия убраны из hero-зоны, а progress-блок сокращён до 3-4 самых полезных сигналов, чтобы экран читался как итог рана и следующий шаг, а не как длинный отчёт
- `Мастерская` получила ещё один readability-pass: убран дублирующий верхний recommendation-banner, служебный footer больше не конкурирует с pager на тесных desktop, medium-height desktop автоматически показывают меньше карточек на страницу, а сами карточки, кнопка покупки и прогресс-строка стали крупнее
- expanded `Задания` / weekly-блок тоже получили readability-pass: short-desktop версия стала чуть выше, liveops/daily/weekly тексты и mission-rows укрупнены, а weekly progress внутри карточки перестал быть микротекстом
- compact/minimal summary в меню тоже перепакован: три статус-карточки `награды / сегодня / неделя` получили больше высоты и крупнее типографику, поэтому первый экран меньше похож на микро-дашборд и быстрее объясняет состояние liveops без открытия `Заданий`
- rewarded-toggle и related copy дочищены: toggle стартового бонуса в advanced-меню стал крупнее и понятнее на compact/minimal, а русские daily-формулировки окончательно вычищены от `дейлик` в пользу `ежедневного заезда`
- для high-resolution desktop menu-layout усилен ещё раз: `full`-экраны теперь растят меню не порогово, а плавно вместе с разрешением, сильнее увеличивая panel/title/CTA и preview-зону; в последних pass split-layout ещё сильнее раздвинут по ширине и высоте, композиция опущена ниже, сама preview-сцена масштабируется вместе с экраном, а верхний chrome (`кошелёк`, `настройки`, `мастерская`, `рейтинг`) тоже укрупняется, чтобы на 2K+ desktop весь интерфейс ощущался цельным, а не собранным из блоков разных размеров
- in-run HUD и экран улучшений дочищены для compact/mobile: во время upgrade/settings/revive скрывается вторичный HUD и тач-контролы, мобильный баннер уровня стал компактнее, а transient `WAVE N` больше не пробивается поверх выбора улучшения
- mobile workshop и compact leaderboard прошли дополнительный readability-pass: в `Мастерской` укрупнены description/progress/buy-блоки и pager, а в `Топе пилотов` усилены цель следующей лиги и сами строки рейтинга
- menu/status и compact settings тоже вычищены: верхний запас ресурсов в меню стал читаемым chip вместо плавающей строки, а мобильные `Настройки` убрали слабополезный мелкий hint в пользу более крупных control-rows и action-кнопок
- advanced menu получил ещё один product-pass: под заголовком убран лишний лидербордный шум, summary сокращён до лучшего результата и ближайшей лиги, чтобы экран быстрее вёл к `Играть`, а не выглядел как телеметрическая панель
- главное меню прошло ещё один composition-pass: на desktop/wide-desktop левая hero-панель теперь меньше зависит от декоративной пустоты, title и CTA опущены ближе к центру и лучше рифмуются с preview-блоком справа, поэтому первый экран выглядит как единая игровая сцена, а не как два случайно разнесённых прямоугольника

Что уже проверено:

- `npm run typecheck`
- `npm run build`
- `npm run test:unit`
- `npm run test:e2e`
- `npm run audit:ui`
- ручной screenshot smoke для expanded `Заданий` на growing/advanced состояниях

Что это закрывает по модерации:

- переводы и русский copy: критичные daily/results/menu строки переведены и вычищены
- resize / out-of-bounds / overlap: подтверждено type-safe адаптивной логикой и browser smoke на compact viewport
- случайные browser interactions: защита от `contextmenu`, `selectstart`, `dragstart` и системных gesture уже сохранена в приложении
- ощущение незавершённости: убран перегруз первого экрана, действия стали яснее, RV показывается как добровольный и понятный бонус

### Что перегружает новичка

- На первом экране слишком много потенциальных точек входа, если открыть все системы сразу.
- Игроку приходится разбираться не только с core loop, но и с мастерской, рейтингом, дейликами и рекламными бонусами.
- Часть полезной информации подана мелко и конкурирует с главным действием вместо того, чтобы поддерживать его.

### Что мешает пониманию интерфейса

- Главный путь `увидел -> понял -> нажал -> начал играть` должен считываться за 3-5 секунд, без чтения длинных подсказок.
- Ранний UI не должен выглядеть как инструментальная панель или liveops-дашборд.
- Мастерская и рейтинг сейчас легко превращаются в плотные таблицы/каталоги с одинаково важными решениями.

### Что мешает монетизации

- Rewarded video работает лучше, когда игрок заранее понимает две вещи: что он сейчас увидит рекламу и что получит за это.
- Ранний контакт с рекламными механиками снижает доверие и ухудшает first-time experience.
- Workshop и результаты должны подводить к RV через понятную ценность, а не через давление.

### Что критично для модерации Яндекс Игр

- Все пользовательские строки должны проходить через единый i18n-слой.
- При resize элементы не должны выходить за границы, обрезаться или наезжать друг на друга.
- Взаимодействие с игровым полем не должно вызывать выделение текста или браузерное контекстное меню.
- На старте и во время действий не должно быть технических ошибок, сырых сообщений и ощущения незавершённого продукта.

## 2. Новая progression-модель интерфейса

### Stage A: первый запуск / первые 1-2 сессии

Показываем:

- один доминирующий CTA `Играть`
- одну вторичную кнопку `Обучение`
- очень компактный верхний статус-бар
- одну короткую stage-hint подсказку про базовый loop

Скрываем:

- мастерскую
- рейтинг
- дейлики
- миссии
- сложные валютные и карьерные блоки
- ранние rewarded-стимулы

Цель:

- минимизировать тревожность
- довести игрока до первого забега максимально быстро
- не превращать первый экран в каталог систем

### Stage B: игрок уже сделал несколько запусков

Показываем:

- `Играть` как главный CTA
- `Ежедневка` как понятное вторичное действие
- компактную мастерскую с ограниченным набором карточек
- упрощённый рейтинг: короткий топ + личный результат
- компактный блок прогресса по liveops

Цель:

- ввести мета-прогрессию и повторные цели
- подсветить первый meaningful upgrade
- мягко открыть rewarded как добровольный ускоритель

### Stage C: опытный игрок

Показываем:

- полную навигацию
- полную мастерскую
- расширенный рейтинг
- дополнительные системы, миссии и карьерный слой

Цель:

- дать глубину без ощущения таблицы и “сырых” подсистем
- поддержать retention через buildcraft, челлендж и соревновательный мотив

### Текущая эвристика стадий

Стадии определяются в `src/game/meta/uiProgression.ts` по:

- количеству сессий
- числу завершённых забегов
- лучшей волне
- факту завершения/скипа обучения
- числу купленных meta-нodов

Это правильно как временный продуктовый слой, но позже пороги стоит откалибровать аналитикой.

## 3. Переработка главного экрана

### Целевая иерархия

1. `Играть`
2. полезное вторичное действие по стадии
3. свернутые сервисные/мета-действия

### Требования к экрану

- только один визуально доминирующий CTA
- вторичные действия слабее по контрасту и размеру
- минимум мелкого текста
- hero-область работает как атмосферная поддержка, а не как второй информационный экран
- узкие окна не должны заставлять UI “схлопываться в пыль”

### Что делаем в реализации

- Stage A оставляем как poster-like стартовый экран
- Stage B/C не возвращаем к перегруженному меню: показываем только полезные entry points
- убираем ранние session toast/return toast, если они не критичны для текущей стадии
- не выводим liveops/карьерные детали как плавающий шум возле CTA

### UX-обоснование

- первое решение игрока должно быть очевидным
- полезные системы открываются только после понимания core loop
- ранняя монетизация не конфликтует с доверием

## 4. Переработка мастерской

### Новая модель раскрытия

- Stage A: мастерская скрыта
- Stage B: только базовый полезный набор, 1-2 очевидных направления роста, recommendation сверху
- Stage C: полный каталог, но с короткими превью-описаниями и более читаемой плотностью

### Правила для карточек

- короткий заголовок
- короткое описание-превью вместо технического абзаца
- явный текущий уровень
- явно видимая стоимость
- рекомендованный апгрейд отмечен отдельно

### Что критично для UX

- игрок не должен принимать 10+ одинаково сложных решений сразу
- описания должны объяснять ценность апгрейда, а не внутреннюю механику
- достижимые покупки должны выделяться визуально

### Что критично для монетизации

- мастерская усиливает желание вернуться в забег и собрать ресурсы
- rewarded в этой системе должен считываться как optional accelerator, а не “плати вниманием чтобы играть нормально”

## 5. Переработка рейтинга

### Новая модель раскрытия

- Stage A: рейтинг скрыт
- Stage B: короткий список, место игрока, следующая цель
- Stage C: фильтры, полноценные строки ранжирования, карьерный прогресс и platform summary только когда хватает места и плотность остаётся читаемой

### Принципы

- главное для раннего этапа: личный результат и ближайшая цель
- лишние цифры и второстепенные метрики убираем из первого взгляда
- поздние детали раскрываем только тогда, когда размер окна позволяет это показать без “табличного микротекста”

## 6. Типографика и layout

### Базовая типографическая система

- экрановый заголовок: 36-52 px
- stage hint / главный supporting text: 14-18 px
- primary CTA: 22-30 px
- secondary CTA: 14-18 px
- карточки мастерской: title 13-18 px, body не ниже 11-13 px в зависимости от плотности
- ключевые summary / leaderboard / results тексты: не ниже 12-14 px

### Layout-принципы

- safe-area мышление и margin budget для всех панелей
- отдельные режимы для full / compact / minimal viewport
- адаптивная сетка вместо попытки “ужать всё масштабом”
- перенос информации в следующую стадию раскрытия, а не в микрошрифт

### Что обязательно проверить

- `1600x900`
- `1280x720`
- `900x500`
- `680x380`
- RU и EN строки на тех же разрешениях

## 7. Локализация

### Принципы

- все строки UI, модалок, подсказок, ошибок и rewarded CTA должны жить в `src/i18n/localization.ts`
- нельзя оставлять хардкод в UI-слое
- строки должны выдерживать RU/EN без поломки контейнеров

### Обязательный QA-чек

- меню
- обучение
- HUD
- мастерская
- рейтинг
- результаты
- revive / reroll / x2 results
- ошибки старта и runtime overlay

## 8. RV / монетизация

### Продуктовая логика

- на Stage A rewarded не должен быть частью первого впечатления
- на Stage B rewarded появляется как добровольный бонус с понятной ценностью
- на Stage C rewarded можно интегрировать глубже в retention/liveops, но без маскировки под обычное действие

### Правила формулировок

Используем прямую структуру:

- `Смотреть рекламу и получить x2 награду`
- `Смотреть рекламу и обновить выбор`
- `Смотреть рекламу и вернуться`
- `Смотреть рекламу и стартовать с бонусом`

### UX-точки показа

- после завершённого действия
- в понятной паузе
- рядом с добровольным бонусом
- без блокировки прогресса

### Что повышает конверсию в RV

- награда понятна до клика
- ценность награды видна до клика
- early game не выглядит как ad trap
- CTA не спорит с основным потоком игры

## 9. SDK / технические исправления

### Обязательный платформенный минимум

- SDK встроен через корректный Yandex flow
- `LoadingAPI.ready()` вызывается в момент готовности к игре
- `GameplayAPI.start()` / `GameplayAPI.stop()` вызываются в корректных точках
- реклама вызывается только через SDK
- pause/resume платформы обрабатываются без поломки состояния

### Production polish

- никаких сырых runtime message / stack trace в интерфейсе
- читаемый fatal overlay вместо браузерной ошибки
- отключены browser selection/context menu на игровом поле
- Yandex media / preview tooling должен быть синхронизирован с staged UI

## 10. Пошаговый implementation plan

### P0: повторная модерация и первый UX-слой

- финализировать staged main menu
- добить крупную типографику на ключевых экранах
- вычистить ранний UI-шум и случайные session toast
- проверить resize на целевых разрешениях
- проверить RU/EN smoke pass
- прогнать `build:yandex` и smoke-test в draft

### P1: retention и soft monetization

- доработать workshop categories / progressive grouping
- калибровать thresholds Stage A/B/C аналитикой
- улучшить results hierarchy и value-preview для rewarded
- упростить поздний leaderboard, если он снова начинает выглядеть как таблица

### P2: продуктовый polish

- вынести stage thresholds в data-config
- добавить визуальный regression pass для RU/EN + viewport matrix
- расширить guided recommendations в workshop и liveops

## 11. Что уже начато в коде

На текущем шаге уже внедряются изменения:

- ранние session toast на меню убраны для starter/growing, чтобы не шуметь на первом экране
- rewarded copy стала более прямой и явно рекламной
- мастерская получила более короткие описания карточек и крупнее базовую типографику
- расширенный слой рейтинга теперь показывается только когда экран реально выдерживает такую плотность
- стартовый loading screen стал локализованным и выглядит как законченный продукт, а не технический preload bar
- runtime HUD теперь тоже раскрывается по стадиям: новичок видит только минимум статусов, а поздний игрок получает более полный combat context
- Yandex media capture и e2e smoke приводятся в соответствие staged UI, чтобы QA и промо-скриншоты не ломались из-за скрытого `Daily`
- e2e теперь дополнительно покрывает compact viewport и RU/EN matrix, включая проверку, что ключевые текстовые слои `menu / ui / upgrade / results` остаются внутри экрана
- visual audit matrix теперь можно собрать одной командой `npm run audit:ui`; она сохраняет локализованные desktop/mobile screenshots и gallery-view в `artifacts/ui-audit/matrix`
- отдельный publish-like smoke для `VITE_PLATFORM_ADAPTER=yandex` теперь можно прогонять командой `npm run audit:yandex`; он проверяет boot без fatal overlay, lifecycle hooks, rewarded/interstitial flow и browser interaction guards на локальном preview со `sdk.js` stub

## Итог

Цель редизайна не “сделать интерфейс красивее”, а:

- ускорить вход в игру
- убрать тревожность и ощущение сырого прототипа
- поэтапно раскрывать глубину
- усилить retention и soft monetization
- закрыть реальные причины прошлых замечаний модерации Яндекс Игр

Документ должен использоваться как рабочая спецификация для UI, frontend, QA и publish-проверки.
